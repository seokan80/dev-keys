## 세 가지 방식 — 고르는 기준

4부의 세 세트는 팀이 일하는 방식 셋을 하나씩 따라 친다. 어느 것이 맞는지는 **얼마나 자주 배포하나**, **검증(QA)을 어디서 하나** 로 갈린다.

| 항목           | GitHub Flow                  | 트렁크 기반 + 기능 플래그                              | 환경 브랜치                                         |
| -------------- | ---------------------------- | ------------------------------------------------------ | --------------------------------------------------- |
| 브랜치         | main + 짧은 기능 브랜치      | main + 몇 시간짜리 브랜치, 릴리스 브랜치는 필요할 때만 | main · stage · dev + 기능 브랜치                    |
| 배포           | PR 을 합치면 main 이 배포    | main 을 자주 배포, 기능은 플래그로 연다                | 브랜치마다 서버 (dev 개발 · stage 검증 · main 운영) |
| 개발 서버 역할 | PR 미리보기                  | PR 미리보기 · 플래그를 켠 계정                         | dev 브랜치                                          |
| "이번엔 A 만"  | A 의 PR 만 합친다            | A 의 플래그만 켠다                                     | 통과한 기능 브랜치만 stage 에 merge                 |
| 핫픽스         | 같은 길 (브랜치 → PR)        | main 에 먼저 → 릴리스 브랜치로 `cherry-pick -x`        | 태그에서 따서 main → stage → dev                    |
| 맞는 팀        | 하루에도 여러 번 배포하는 웹 | 배포가 아주 잦고 자동 테스트가 탄탄한 팀               | QA 서버가 따로 있고 기능마다 배포 시점이 다른 팀    |

- 앱스토어 심사를 거치는 앱 · 설치형 제품처럼 **버전을 붙여 내고 여러 버전을 지원하면** GitFlow(develop · release · hotfix 브랜치)나 릴리스 브랜치 방식을 본다. GitFlow 를 만든 사람도 2020년에 "계속 배포하는 웹이면 GitHub Flow 같은 더 단순한 흐름을" 이라고 덧붙였다
- dev 에 다 합치고 stage 로 **커밋을 골라 cherry-pick** 하는 방식도 현장에 있지만, 빠뜨림 · 충돌 · 해시가 다른 같은 변경이 쌓여 바꾼 사례가 많다 (환경 브랜치 해설)

## 트렁크 기반 개발

모두가 **main(트렁크) 하나에 작게, 하루에도 여러 번** 합친다. 브랜치를 쓰더라도 몇 시간 · 하루 안에 합친다. 오래 사는 기능 브랜치가 없으니 큰 충돌이 생기지 않고, main 은 늘 배포할 수 있다.

- 합치기 전에 받아서 위로: `git pull --rebase` (또는 `pull.rebase true`)
- 커밋마다 자동 테스트 — main 이 깨지면 다른 일보다 먼저 고친다
- 큰 기능은 **기능 플래그 뒤에서** 나눠 합친다

## 기능 플래그

코드는 배포돼 있어도 **켜기 전에는 사용자에게 보이지 않게** 하는 스위치. 배포(코드를 서버에 올리기)와 출시(사용자에게 열기)를 나눈다.

| 종류                     | 하는 일                                        | 수명         |
| ------------------------ | ---------------------------------------------- | ------------ |
| 출시 플래그 (release)    | 미완성 기능을 숨겼다가 다 되면 연다 (이 세트)  | 며칠 ~ 몇 주 |
| 실험 플래그 (experiment) | 사용자 일부에게만 열어 A/B 비교                | 실험 동안    |
| 운영 스위치 (ops)        | 문제가 생기면 무거운 기능을 끈다 — kill switch | 길게         |

- 파일(`flags.json`)로 두면 켜고 끄는 데 배포가 필요하다. 설정 서비스(LaunchDarkly · Unleash · Firebase Remote Config …)로 두면 배포 없이 바꾼다
- **플래그는 빚이다.** 켠 상태와 끈 상태를 둘 다 시험해야 하고, 쌓이면 조합이 늘어난다. 다 쓴 출시 플래그는 바로 지운다 (이 세트의 마지막 커밋)

## 릴리스는 태그, 릴리스 브랜치는 필요할 때만

- 보통은 main 의 커밋에 태그를 붙여 내보낸다 (3부 "태그와 릴리스")
- 내보낸 버전을 고쳐야 하는데 main 에 아직 내보낼 수 없는 것이 들어 있을 때만, **그 태그에서** 릴리스 브랜치를 딴다
- **수정은 main 에 먼저(upstream first)** → 릴리스 브랜치로 `cherry-pick -x`. 릴리스 브랜치에만 고치면 다음 릴리스에서 버그가 되살아난다
- 릴리스 브랜치는 main 으로 다시 합치지 않는다 — 수정은 이미 main 에 있다. 다 쓰면 태그를 남기고 지운다
- `-x` 의 `(cherry picked from commit …)` 줄로 어느 수정이 어디까지 갔는지 찾는다

## AI 에이전트와 쓸 때

- **작게 자주가 에이전트에게도 맞다.** 에이전트에게 큰 기능을 한 번에 맡기지 말고, 플래그 뒤에서 합칠 수 있는 단위로 나눠 맡긴다
- **플래그 정리를 할 일로 남긴다.** "출시 뒤 2주가 지난 플래그 지우기" 는 에이전트에게 맡기기 좋은 일이다 — 플래그 이름으로 코드를 찾아 지우고, 테스트로 확인한다
- **백포트도 맡길 수 있다.** "main 의 abc1234 를 release/1.3 에 `cherry-pick -x` 하고 테스트" — 충돌이 나면 사람에게 넘기게 한다
