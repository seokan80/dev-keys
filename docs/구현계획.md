# DevKeys 구현 계획

> 작성일: 2026-10-16
> 기준 문서: [`개발계획서.md`](개발계획서.md) (이하 "계획서")
> 용도: 계획서를 Claude Code 작업 단위로 쪼갠 실행 계획. 계획서의 결정은 그대로 두고 **빠진 것·모순·구체화가 필요한 것**만 보완한다. 계획서를 대체하지 않는다.

---

## 0. 요약

- 계획서의 범위와 마일스톤(M0~M7)은 그대로 진행할 수 있다. 다만 **착수 전에 정할 것**(1장)과 **스키마·엔진 보완 21건**(2장)이 있다.
- 가장 큰 구멍 네 가지
  1. 문제(item)에 고유 id가 없음 → 최고 기록·오답 기록이 꼬일 수 있음
  2. Git 커밋 모델에 "복사됨" 관계가 없음 → 계획서 4.4의 rebase/cherry-pick 결과 비교를 할 수 없음
  3. 스테이징이 없어서 `reset --soft`와 `--hard`의 결과가 같음 → 엔진으로 동의어를 판정하면 `--soft`를 `--hard` 정답으로 인정함
  4. Cloudflare Web Analytics에는 사용자 정의 이벤트가 없음 → 세트 완료율·방문당 세트 수를 잴 수 없음
- 순서: M0 → M1 → M2 → M5가 주 경로. **M3(Git 엔진)은 UI와 무관한 순수 로직이라 M0 직후부터 병행할 수 있다.**
- 미션 데이터는 goal을 손으로 쓰지 말고 **시작 명령 + 권장 풀이**만 쓰고, goal은 빌드 때 생성하는 쪽을 권장 (5.3).
- Git 엔진은 **실제 git과 대조하는 테스트**를 두어 "틀린 git을 가르치는" 사고를 막는다 (M3).
- 보완 항목을 더해도 계획서 추정(8~10주) 안에 들어가지만, 상단(10주)에 가까울 것으로 본다.

## 1. 착수 전 결정

### 1.1 개인 기본 스택과 다름 — 계획서안으로 확정 (2026-10-16)

개인 기본값은 **Spring Boot + React, Gradle(Kotlin DSL)** 인데, 계획서 2장은 **Astro + React + TS(npm), MVP 백엔드 없음 → 2차 Cloudflare Workers + D1** 이다.

- **결정: 계획서안 유지** (2026-10-16 확정). 0장 확정 사항 "MVP는 정적 사이트로 0원"과 세트별 정적 페이지(SEO)에는 서버가 필요 없고, 상시 떠 있는 JVM 서버는 무료로 두기 어렵다. 2차 순위 API도 엔드포인트 몇 개라 Workers로 충분하다.
- 저장소에 올리는 규칙 파일(`AGENTS.md`, 아래 M0 참고) 첫머리에 "이 프로젝트는 npm + Astro. 개인 기본값(Spring/Gradle)을 적용하지 않음"을 적어서, 다음 세션이 개인 기본값으로 되돌리지 않게 한다.
- 개인 규칙의 취지(버전을 한곳에 모으고 도구 버전을 고정)는 npm에서 `package-lock.json` 커밋, `.nvmrc`, `package.json`의 `engines`·`packageManager` 필드로 대신한다.

## 2. 계획서 검토 — 보완할 곳

### 2.1 데이터

| # | 위치 | 문제 | 보완 |
|---|---|---|---|
| 1 | 5장 세트 | 문제에 id가 없다. 기록을 "세트 + 순번"으로 저장하면 문제를 하나 끼워 넣는 순간 기록이 엉뚱한 문제로 옮겨 간다 | `items[].id` 필수. 저장 키는 `세트id/문제id` |
| 2 | 5장 세트 | "다음 세트 추천"의 순서를 정할 필드가 없다 | `order`(카테고리 안 순서) 추가. `level`은 표시용 |

| 4 | 4.5 | 엔진으로 동의어를 판정하려면 "어떤 상태에서 실행하는지"가 필요하다. `reset --hard HEAD~1`, `merge feature`는 빈 저장소에서 실행할 수 없다 | recall 문제에 `context.setup`(명령 목록) 추가. 엔진이 모르는 명령(`add`, `status`, `log`, `push`, `stash` …)은 문자열 비교만 |
| 5 | 4.3 / 4.4 | `Commit` 타입에 복사·되돌림 원본 정보가 없어 4.4의 비교 기준 3을 구현할 수 없다 | `origin` 필드 추가 (5.1) |
| 6 | 5장 미션 | start·goal을 RepoState로 직접 쓰면 길고 틀리기 쉽다 | start는 **명령 목록**, goal은 **권장 풀이를 실행한 결과로 빌드 때 생성** + 텍스트 스냅샷으로 사람이 한 번 검수 (5.3) |

## 3. 작업 순서

```
M0 셋업 ─► M1 타이핑·키보드 ─► M2 기본 모드 ──────────► M5 도전 모드·SRS ─► M6 ─► M7 공개
  │                                              ▲
  └─► M3 Git 엔진 ─► M4 트리·미션 ────────────────┘  (M5의 Git 동의어 판정에 M3 필요)

M6 콘텐츠 작성: 세트는 M2(세트 스키마), 미션은 M4(미션 스키마) 이후 언제든
```

- 혼자 순서대로 하면 계획서 순서 그대로(M0 → M1 → …) 간다.
- 병행하려면 M3만 떼어 내면 된다. `src/core/git` 밖을 건드리지 않아서 충돌이 거의 없다.
- 위험이 가장 큰 것은 M3·M4(엔진 정확성, 트리 레이아웃)다. 일정이 밀리면 미션 수(5~10)를 줄이고 엔진 품질은 지킨다.

## 5. 설계 보완 (코드 수준)

### 5.1 Git 상태 모델 (계획서 4.3 수정)

```ts
type Commit = {
  id: string                 // 내부 id: 'c1', 'c2' … (결정적 순번)
  label: string              // 화면·명령용: 'C1', 복사본은 "C3'", "C3''"
  parents: string[]          // [0] = 첫 부모
  origin?: { kind: 'copy' | 'revert'; of: string }  // of = 최초 원본 id (복사의 복사도 최초 원본을 가리킴)
  message?: string
}

type RepoState = {
  commits: Record<string, Commit>
  branches: Record<string, string>   // 브랜치명 → 커밋 id
  head: { type: 'branch'; name: string } | { type: 'detached'; commit: string }
  previous?: Head                    // 바로 전 HEAD (switch - · checkout -)
  seq: number                        // 다음 커밋 순번
}

type GitEvent =                       // 그림(애니메이션)용
  | { type: 'commit'; id: string }
  | { type: 'copy'; from: string; to: string }
  | { type: 'branch'; name: string; from: string | null; to: string | null }  // from null = 만듦, to null = 지움
  | { type: 'head'; from: Head; to: Head }
  | { type: 'orphaned'; ids: string[] }

type ExecResult = {
  state: RepoState
  events: GitEvent[]
  output: string                     // "Fast-forward", "Already up to date." 등. 없으면 ''
  error: { message: string; hint: string } | null   // 실제 git 문구 + 한 줄 한국어 설명
  info: { command: string; resetMode?: 'soft' | 'mixed' | 'hard' }   // 동의어 판정용
}
```

- 초기 저장소: `main` 브랜치 하나, 커밋 `C1` 하나.
- 상태는 불변이다. `execute`는 새 객체를 돌려준다(처음부터 다시·스냅샷이 쉬움).

### 5.2 결과 트리 비교 (계획서 4.4 구체화)

```
sig(c) = c가 시작 상태에 있던 커밋이면  c.id
         아니면  hash(kind, sig(origin.of), sig(parents[0]), sig(parents[1]), …)
                 kind = origin.kind, origin이 없으면 'new'
```

- 판정: ① 브랜치 이름 집합이 같고 ② 브랜치마다 가리키는 커밋의 sig가 같고 ③ HEAD가 같은 브랜치(detached면 같은 sig)
- sig에 조상 전체가 담기므로 그래프 형태(계획서 기준 3)는 ②·③에서 함께 확인된다. 고아 커밋은 보지 않는다.
- 커밋을 만든 순서가 달라도(내부 id가 달라도) 구조가 같으면 같다고 판정된다.
- rebase와 cherry-pick 연속은 같은 결과(정답), rebase와 merge는 다른 결과다.
- 반환값은 `{ equal, diffs }`. diffs로 "feature 위치가 목표와 다름", "hotfix 브랜치가 없음" 같은 힌트를 보여 줄 수 있다.

코드 세트 — `content/sets/java/stream-basics.yaml` (M2에서 정한 형식)
```yaml
id: java-stream-basics
category: java
order: 1
title: Stream 기본
description: filter · map · groupingBy · joining 으로 컬렉션 다루기   # 카테고리 목록·검색 설명

  - id: orders

      List<String> paid = orders.stream()
          .filter(o -> "PAID".equals(o.status()))

          .toList();
    notes:                       # 줄별 해설. at 은 그 줄에만 있는 글자 (정확히 한 줄에 맞아야 한다)
      - at: .toList();
        note: Java 16+. 수정할 수 없는 List 를 돌려준다
    hidden:                      # 치지 않는 앞뒤 코드 — 컴파일 검증용 (M6)
      before: |-
        import java.util.*;
        class StreamBasics { void run(List<Order> orders) {
      after: '} }'
```

- 해설 파일은 `content/guides/<category>/<slug>.md`로 정해져 있어 `guide` 필드를 두지 않는다(어긋날 일이 없다). MDX는 필요해지면 쓴다
- `note`(문제 설명)는 문제 첫 줄 위에, `notes`(줄별)는 해당 줄 위에 주석처럼 보인다. 둘 다 있으면 둘 다
- `output`(명령 출력)은 문제 마지막 줄을 치고 Enter 를 누르면 그 아래에 나온다. ASCII · 탭 없음 · 100자 이하
- `scene`(그림, 문제 마지막 줄): `workdir` · `staged` · `repo` 표 목록(최신 커밋이 앞, "~" 로 시작하면 사라진 것), `arrow: { from, to, label }`, `compare: [칸, 칸]`, `caption`
- 커밋 트리 그림(M4 PR B): 세트에 `engine: { root: '<해시> <메시지>' }` 를 두면 copy 명령을 Git 엔진으로 차례로 돌린다. 문제마다
  - `tree: { caption }` — Enter 뒤에 이 명령 전 · 후 커밋 트리
  - `before: [명령]` — 치지 않고 엔진에서만 먼저 실행 (이야기 속 "커밋한 뒤"). 커밋 메시지 앞 7자리를 해시로 쓰면 그림 설명이 출력과 맞는다
  - `skipEngine: true` — 트리와 상관없는 명령(stash · log · branch --merged)은 엔진에서 뺀다. `tree` 와 함께 못 쓴다
  - `hash` — 이 명령이 만든 커밋(머지 커밋 등)에 붙일 7자리 해시
  - engine 세트의 명령은 한 줄씩, 이 칸들은 engine 세트에서만 쓴다
- `notes[].result`(결과 값): 그 줄을 다 치면 아래에 보인다. 변수는 `이름 = 값`, 요청은 `GET … → 200 OK …`
- 줄 번호 대신 `at`(글자 조각)으로 줄을 찾는 이유: 코드를 고쳐 줄이 밀려도 해설이 따라가고, 검수할 때 어느 줄 설명인지 바로 보인다
- goal을 엔진이 만들면 엔진 버그가 goal에 섞일 수 있다. 그래서 미션마다 goal의 텍스트 그래프를 스냅샷 테스트로 고정해 처음 한 번 사람이 확인하고, M3의 실제 git 대조 테스트가 한 번 더 막는다.

### 5.4 점수 (계획서 4.6 구체화 — 제안값)

| 대상 | 공식 |
|---|---|
| recall 문제 | 정답 100 / 첫 글자 힌트 후 정답 60 / 오답·정답 보기 0 (오답 목록 등록) |
| 도전 모드 세트 | Σ 문제 점수 × (0.5 + 0.5 × 정확도) |
| 미션 | 성공 시 max(100, 1000 + 남은 초 × 10 − 권장 초과 명령 수 × 100), 실패·시간 초과 0 |

- 상수는 `core/scoring/constants.ts` 한곳에 둔다. 2차 서버도 이 파일을 그대로 쓴다.
- 도전 모드의 정확도(M5 결정): 친 글자 중 지우지 않은 비율 `1 − 지운 글자 / 친 글자`. 따라치기처럼 기준 글이 없으니 오타 대신 고쳐 친 정도로 본다. 틀린 뒤 따라 치는 글자는 세지 않는다
- 도전 모드 최고 기록은 점수로 비교한다(`bests[`${setId}:recall`].score`)

## 7. 작업 방식

- 마일스톤 하나 = 이슈 1개 + 브랜치 1개(`m1-typing` 식) → PR(미리보기 확인) → main 병합·배포
- **병합·배포가 끝나면 바로** 브랜치와 작업 트리를 지운다: `git worktree remove --force <경로>` → `git branch -d <브랜치>`
- 작업 트리는 M3를 M1·M2와 병행할 때처럼 실제로 동시에 진행할 때만 만든다. 만들기 전에 `git worktree list`로 쌓인 게 없는지 본다
- core는 테스트를 먼저 쓰고 구현한다
- 마일스톤이 끝나면 계획서의 체크박스와 이 문서를 함께 갱신한다
