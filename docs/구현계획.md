# DevKeys 구현 계획

> 작성일: 2026-10-16
> 기준 문서: [`개발계획서.md`](개발계획서.md) (이하 "계획서")
> 용도: 계획서를 Claude Code 작업 단위로 쪼갠 실행 계획. 계획서의 결정은 그대로 두고 **빠진 것·모순·구체화가 필요한 것**만 보완한다. 계획서를 대체하지 않는다.

---

## 0. 요약

- 계획서의 범위와 마일스톤(M0~M7)은 그대로 진행할 수 있다. 다만 **착수 전에 정할 것**(1장)과 **스키마·엔진 보완 21건**(2장)이 있다.
- 가장 큰 구멍 네 가지
  1. 문제(item)에 고유 id가 없음 → 최고 기록·오답 기록이 꼬일 수 있음
  2. Git 커밋 모델에 "복사됨" 관계가 없음 → 계획서 4.4의 rebase/cherry-pick 결과 비교를 할 수 없음
  3. 스테이징이 없어서 `reset --soft`와 `--hard`의 결과가 같음 → 엔진으로 동의어를 판정하면 `--soft`를 `--hard` 정답으로 인정함
  4. Cloudflare Web Analytics에는 사용자 정의 이벤트가 없음 → 세트 완료율·방문당 세트 수를 잴 수 없음
- 순서: M0 → M1 → M2 → M5가 주 경로. **M3(Git 엔진)은 UI와 무관한 순수 로직이라 M0 직후부터 병행할 수 있다.**
- 미션 데이터는 goal을 손으로 쓰지 말고 **시작 명령 + 권장 풀이**만 쓰고, goal은 빌드 때 생성하는 쪽을 권장 (5.3).
- Git 엔진은 **실제 git과 대조하는 테스트**를 두어 "틀린 git을 가르치는" 사고를 막는다 (M3).
- 보완 항목을 더해도 계획서 추정(8~10주) 안에 들어가지만, 상단(10주)에 가까울 것으로 본다.

## 1. 착수 전 결정

### 1.1 개인 기본 스택과 다름 — 계획서안으로 확정 (2026-10-16)

개인 기본값은 **Spring Boot + React, Gradle(Kotlin DSL)** 인데, 계획서 2장은 **Astro + React + TS(npm), MVP 백엔드 없음 → 2차 Cloudflare Workers + D1** 이다.

- **결정: 계획서안 유지** (2026-10-16 확정). 0장 확정 사항 "MVP는 정적 사이트로 0원"과 세트별 정적 페이지(SEO)에는 서버가 필요 없고, 상시 떠 있는 JVM 서버는 무료로 두기 어렵다. 2차 순위 API도 엔드포인트 몇 개라 Workers로 충분하다.
- 저장소에 올리는 규칙 파일(`AGENTS.md`, 아래 M0 참고) 첫머리에 "이 프로젝트는 npm + Astro. 개인 기본값(Spring/Gradle)을 적용하지 않음"을 적어서, 다음 세션이 개인 기본값으로 되돌리지 않게 한다.
- 개인 규칙의 취지(버전을 한곳에 모으고 도구 버전을 고정)는 npm에서 `package-lock.json` 커밋, `.nvmrc`, `package.json`의 `engines`·`packageManager` 필드로 대신한다.

## 2. 계획서 검토 — 보완할 곳

### 2.1 데이터

| # | 위치 | 문제 | 보완 |
|---|---|---|---|
| 1 | 5장 세트 | 문제에 id가 없다. 기록을 "세트 + 순번"으로 저장하면 문제를 하나 끼워 넣는 순간 기록이 엉뚱한 문제로 옮겨 간다 | `items[].id` 필수. 저장 키는 `세트id/문제id` |

## 3. 작업 순서

```
M0 셋업 ─► M1 타이핑·키보드 ─► M2 기본 모드 ──────────► M5 도전 모드·SRS ─► M6 ─► M7 공개
  │                                              ▲
  └─► M3 Git 엔진 ─► M4 트리·미션 ────────────────┘  (M5의 Git 동의어 판정에 M3 필요)

M6 콘텐츠 작성: 세트는 M2(세트 스키마), 미션은 M4(미션 스키마) 이후 언제든
```

- 혼자 순서대로 하면 계획서 순서 그대로(M0 → M1 → …) 간다.
- 병행하려면 M3만 떼어 내면 된다. `src/core/git` 밖을 건드리지 않아서 충돌이 거의 없다.
- 위험이 가장 큰 것은 M3·M4(엔진 정확성, 트리 레이아웃)다. 일정이 밀리면 미션 수(5~10)를 줄이고 엔진 품질은 지킨다.

## 5. 설계 보완 (코드 수준)

### 5.1 Git 상태 모델 (계획서 4.3 수정)

```ts
type Commit = {
  id: string                 // 내부 id: 'c1', 'c2' … (결정적 순번)
  label: string              // 화면·명령용: 'C1', 복사본은 "C3'", "C3''"
  parents: string[]          // [0] = 첫 부모
  origin?: { kind: 'copy' | 'revert'; of: string }  // of = 최초 원본 id (복사의 복사도 최초 원본을 가리킴)
  message?: string
}

type RepoState = {
  commits: Record<string, Commit>
  branches: Record<string, string>   // 브랜치명 → 커밋 id
  head: { type: 'branch'; name: string } | { type: 'detached'; commit: string }
  previous?: Head                    // 바로 전 HEAD (switch - · checkout -)
  seq: number                        // 다음 커밋 순번
}

type GitEvent =                       // 그림(애니메이션)용
  | { type: 'commit'; id: string }
  | { type: 'copy'; from: string; to: string }
  | { type: 'branch'; name: string; from: string | null; to: string | null }  // from null = 만듦, to null = 지움
  | { type: 'head'; from: Head; to: Head }
  | { type: 'orphaned'; ids: string[] }

type ExecResult = {
  state: RepoState
  events: GitEvent[]
  output: string                     // "Fast-forward", "Already up to date." 등. 없으면 ''
  error: { message: string; hint: string } | null   // 실제 git 문구 + 한 줄 한국어 설명
  info: { command: string; resetMode?: 'soft' | 'mixed' | 'hard' }   // 동의어 판정용
}
```

- 초기 저장소: `main` 브랜치 하나, 커밋 `C1` 하나.
- 상태는 불변이다. `execute`는 새 객체를 돌려준다(처음부터 다시·스냅샷이 쉬움).

### 5.2 결과 트리 비교 (계획서 4.4 구체화)

```
sig(c) = c가 시작 상태에 있던 커밋이면  c.id
         아니면  hash(kind, sig(origin.of), sig(parents[0]), sig(parents[1]), …)
                 kind = origin.kind, origin이 없으면 'new'
```

- 판정: ① 브랜치 이름 집합이 같고 ② 브랜치마다 가리키는 커밋의 sig가 같고 ③ HEAD가 같은 브랜치(detached면 같은 sig)
- sig에 조상 전체가 담기므로 그래프 형태(계획서 기준 3)는 ②·③에서 함께 확인된다. 고아 커밋은 보지 않는다.
- 커밋을 만든 순서가 달라도(내부 id가 달라도) 구조가 같으면 같다고 판정된다.
- rebase와 cherry-pick 연속은 같은 결과(정답), rebase와 merge는 다른 결과다.
- 반환값은 `{ equal, diffs }`. diffs로 "feature 위치가 목표와 다름", "hotfix 브랜치가 없음" 같은 힌트를 보여 줄 수 있다.

- `output`(명령 출력)은 문제 마지막 줄을 치고 Enter 를 누르면 그 아래에 나온다. ASCII(CLI 기호 ✓ ✗ • → … 는 된다) · 탭 없음 · 120자 이하
- `scene`(그림, 문제 마지막 줄): `workdir` · `staged` · `repo` 표 목록(최신 커밋이 앞, "~" 로 시작하면 사라진 것), `arrow: { from, to, label }`, `compare: [칸, 칸]`, `caption`
- 커밋 트리 그림(M4 PR B): 세트에 `engine: { root: '<해시> <메시지>' }` 를 두면 copy 명령을 Git 엔진으로 차례로 돌린다. 문제마다
  - `tree: { caption }` — 그 줄을 끝냈을 때 커밋 그래프 아래 설명 (그래프는 engine 세트에서 늘 보인다, 이슈 #28)
  - `before: [명령]` — 치지 않고 엔진에서만 먼저 실행 (이야기 속 "커밋한 뒤"). 커밋 메시지 앞 7자리를 해시로 쓰면 그림 설명이 출력과 맞는다
  - `skipEngine: true` — 트리와 상관없는 명령(stash · log · branch --merged)은 엔진에서 뺀다. `tree` 와 함께 못 쓴다
  - `hash` — 이 명령이 만든 커밋(머지 커밋 등)에 붙일 7자리 해시
  - `as` — 엔진이 모르는 명령을 엔진에서는 이 명령으로 돌린다 (`git worktree add … -b X` → `git branch X`)
- 한 줄 길이(2026-10-17): 코드는 읽기 좋게 80자, Git 세트(터미널 명령)는 한 줄로 길어지기 쉬워 100자까지 (`--trailer` 처럼 긴 명령)
- `prompt`(모든 세트): 대화형 질문에 답하는 줄 — `$` 대신 그 질문을 앞에 보여 준다 (`git add -p` 의 `y` · `n`). 한 줄 · ASCII. 이야기에서는 `run '명령' y n` 으로 질문이 뜰 때 답을 넣어(`scripts/pty-run.py`) 실제 출력을 뽑고, `git-story-check` 는 답 줄을 앞 명령의 출력과 함께 맞춰 본다
  - engine 세트의 명령은 한 줄씩, 이 칸들은 engine 세트에서만 쓴다
- `notes[].result`(결과 값): 그 줄을 다 치면 아래에 보인다. 변수는 `이름 = 값`, 요청은 `GET … → 200 OK …`
- 줄 번호 대신 `at`(글자 조각)으로 줄을 찾는 이유: 코드를 고쳐 줄이 밀려도 해설이 따라가고, 검수할 때 어느 줄 설명인지 바로 보인다
- goal을 엔진이 만들면 엔진 버그가 goal에 섞일 수 있다. 그래서 미션마다 goal의 텍스트 그래프를 스냅샷 테스트로 고정해 처음 한 번 사람이 확인하고, M3의 실제 git 대조 테스트가 한 번 더 막는다.

  - **GitHub Flow** — 합치면 바로 배포. 개발 서버 역할은 PR 미리보기. 핫픽스도 같은 길
  - **트렁크 기반 + 기능 플래그** — 작게 자주 main 에, 미완성 기능은 플래그로 꺼 둔다. 릴리스는 태그, 릴리스 브랜치는 필요할 때만. 수정은 main 먼저 → `cherry-pick -x` (upstream first)
  - **환경 브랜치** — QA 서버가 따로 있고 기능마다 배포 시점이 다른 팀(컬리 · 당근 · LINE 사례). feature 는 main 에서 따서 dev · stage 에 **각각 merge**, stage → main 은 `merge --ff-only` + 태그, 핫픽스는 태그에서 따서 main → stage → dev, dev 는 버려도 되는 브랜치(가끔 main 에서 다시 만든다)
  - dev 에 다 합치고 stage 로 cherry-pick 해 올리는 방식은 현장에 있지만 누락 · 충돌 · 해시 불일치로 버린 사례가 많다(LINE 2023 · Meta 2016). 환경 브랜치 세트 뒷부분에서 위험과 점검(`git cherry -v`, `branch --merged` 가 모르는 것)만 다룬다
  - git-flow 는 해설 비교표에서 앱 · 설치형 제품용으로만. 근거 자료는 GitLab Flow(환경 브랜치) · Microsoft Release Flow · trunkbaseddevelopment.com · gitworkflows · Raymond Chen "Stop cherry-picking, start merging"
- 칠 것이 없는 주제(GitHub Pages · Copilot 웹 · PythonAnywhere · Windows 파일명)는 해설 안내만
- **Git 세트는 모두 오른쪽에 그림이 있다** (2026-10-17 사용자 피드백 "2, 3부가 우측에 트리가 나오지 않아"): 1 · 4번은 상태 그림, 나머지는 엔진 커밋 그래프. 엔진 범위는 그대로 두고 세트에서 흉내 낸다 — 원격 브랜치는 `origin/…` · `upstream/…` 이름의 브랜치(GitTree 가 점선으로), 태그는 `tags/…` 이름의 브랜치(`tag: …` 로), fetch 로 들어오는 남의 커밋은 `as` 로 detached HEAD 에서 commit 뒤 이름표 옮기기, rebase -i · amend · rebase --exec 처럼 커밋을 새로 쌓는 명령은 reset + commit, gh 병합은 브랜치 지우기 + pull 때 squash 커밋 하나. 그래프와 상관없는 줄(설정 · 파일 · 보기)은 skipEngine
- Git 목록은 `content/curriculum/git.yaml` 로 부를 나눠 보인다 (부 제목 · 설명 · 세트 · 준비 중 항목). 새 세트는 그 파일의 부에 넣어야 화면에 보인다 — `validate:content` 가 막는다
- 공개 전 우선순위: 1부 ~ 5부 모두 (2026-10-17 3 · 4부까지 만들었다). 이후는 미션 · 코드 세트를 늘린다
- **출력은 실제 git 으로 뽑는다**: 이야기 `content/stories/git/<슬러그>.sh` 를 `scripts/git-story.sh` 가 홈 폴더 · 커밋 시각을 고정해 가상 터미널에서 돌린다(해시가 매번 같다). `npx tsx scripts/git-story-check.ts <슬러그>` 가 세트 출력과 맞춰 본다. Git 세트는 모두 이야기 파일이 있다. **gh 명령**(5부 마지막 · 4부)은 연습용 GitHub 저장소 `seokan80/devkeys-sandbox`(비공개)에서 실제로 실행한다 — 이야기 속 주소가 그 저장소를 가리키게(insteadOf), gh 는 `GH_REPO` 로 묶는다. 실행마다 달라지는 저장소 이름 · PR 번호 · GitHub 가 만든 커밋 해시 · 크기는 `rename` / `rename_re` 로 이야기 속 값으로, 터미널 제어 문자 · 진행 표시 · 압축 스레드 수 · 내려받기 속도는 실행기가 고정한다. 받아 오기(fetch · pull · clone)가 중심인 세트(2부 8~11)는 GitHub 의 `remote:` 숫자가 서버 쪽 압축 상태에 따라 실행마다 달라서 연습용 서버 저장소(`~/server/*.git`, `file://` insteadOf)로 돌린다. 처음 올리기(7번)만 GitHub 연습용 저장소에서(그 안의 clone 장면도 같은 브랜치를 올린 서버 저장소에서 받는다) — GitHub 는 기본 브랜치를 지울 수 없어 `scripts/git-story-sandbox.sh` 가 자리 브랜치 `base` 를 기본으로 비켜 두고 "빈 저장소"를 만든다. GitHub 로 올리면서 받아 오기도 해야 하는 이야기(4부 GitHub Flow)는 `sandbox_split` 으로 올리기만 GitHub(`pushInsteadOf`), 받아 오기는 GitHub 와 맞춘 서버 저장소(`sandbox_sync`)로 나눈다. 실행기의 작업 폴더는 `/tmp/devkeys-git-story` 로 고정한다 — pull 이 만든 머지 메시지에 주소가 들어가도 해시가 같게

### 5.9 명령 찾기 (2026-10-20 결정, 이슈 #59)

사용자: "명령을 쉽게 찾고, 상황을 설명하면 명령을 찾아 주는 기능". 벡터 DB 는 쓰지 않는다 — 말뭉치(명령 200여 개 · 상황 문장 200여 개)가 작고 닫혀 있다. ai-stock-advisor 가 pgvector 를 넣었다 지운 기록(ADR-15 "찾지 말고 전부 읽기")과 sudori 의 "검증된 재료만 · 출력 검사 · 평가 세트"를 따른다.

1. **명령 카탈로그 + 검색 (이 이슈)** — `src/lib/commands/catalog.ts` 가 빌드 때 Git 세트의 따라치기 줄을 명령 모양(도구 · 하위 명령(동작 · config 이름 포함) · 옵션, 값은 뺀다)으로 묶고, 해설 · 실제 출력 · 세트를 예시로, 도전 문제 설명을 "상황"으로 붙인다. `/git/commands`(브라우저 검색 — 명령 조각 · 한국어 낱말 · 두 글자 조각, 조사 떼기) · `/git/commands/<명령>`(상황 · 세트에 나온 모습 · 연습하는 세트 · 같은 명령의 다른 모양). 세트를 더하면 저절로 늘어난다. 명령 주소가 겹치면 `validate:content` 가 막는다
2. **평가 세트** (이슈 #60) — `content/commands/eval.yaml` 에 사람이 칠 법한 상황 질문 102개와 정답 명령 주소(여럿 허용). 정답 명령이 카탈로그에 없으면 `validate:content` 가 막는다. `npm run eval:commands` 가 1위 · 상위 3 · 상위 10 정답률과 놓친 질문을 보이고, `tests/unit/commands/eval.test.ts` 의 기준선 아래로 떨어지면 테스트가 실패한다. 처음 잰 값(2026-10-20): 1위 52% · 상위 3 72% · 상위 10 86% — 놓친 것은 대부분 그 표현의 상황 문장이 없는 명령
3. **상황 문장** (이슈 #61) — `content/commands/situations/<부>.yaml` 에 명령 주소마다 사람이 검색창에 칠 법한 말(2~60자)을 Claude Code 가 쓰고 사람이 검수한다. 카탈로그에 없는 주소 · 두 파일에 같은 주소 · 평가 질문과 같은 문장은 `validate:content` 가 막는다(평가 세트를 베끼면 숫자가 거짓이 된다). 검색은 흔한 낱말(커밋 · 브랜치 · 파일)을 가볍게, 드문 낱말을 무겁게 치고(IDF), 질문이 상황 문장에 붙은 그대로 들어 있으면 더 친다. 카탈로그는 세트를 부 순서로 읽는다(점수가 같으면 앞 부의 명령이 앞). 다시 잰 값(2026-10-20): 1위 66% · 상위 3 86% · 상위 10 94%, 기준선을 60 · 80 · 90 으로 올렸다. 평가 세트와 상황 문장을 같은 AI 가 썼으니 숫자가 부풀었을 수 있다 — 사람이 따로 쓴 질문으로 한 번 더 잰다
   - 놓친 질문을 보고받으면 평가 세트 끝의 "사람이 쓴 질문" 에 먼저 더하고 고친다. 명령이 없으면 세트에 줄을 더하고(이야기로 실제 출력), 말이 달라 못 찾으면 같은 뜻 낱말(`search.ts` 의 `SYNONYMS` — 아이디 · id → 해시, 조회 → 보기)로. 그 질문 하나에 맞춘 상황 문장은 쓰지 않는다 (이슈 #62: "커밋 아이디로 변경 파일 목록 조회" → `git show --name-only <해시>`)
   - 2026-10-28 검색 보완(#63): 받아 오기·가져오기와 합치기·병합의 활용형을 맞추고, `안 …`·`…지 않…`의 동작을 긍정 검색어에서 분리한다. `…만`으로 한정한 낱말을 우선하고 상황의 정확한 일치를 해설의 조각 일치보다 무겁게 친다. 기존 103문항을 바꾸지 않고 1위 79/103(77%) · 상위 3 91/103(88%) · 상위 10 98/103(95%). 기준선 76 · 88 · 95. 일반 한국어 문법 전체를 해석하는 기능은 아니며 조건절·복합 부정은 여전히 한계가 있다. 새 회귀 질문은 개발자가 만든 테스트이고 독립적인 사람 평가로 계산하지 않는다.
4. (숫자를 보고) AI 에게 묻기 — Worker API, 카탈로그 전체를 프롬프트 캐시로 읽고 카탈로그 id 만 고르게. 백엔드 · 비용 상한 · 개인정보 방침 결정 뒤

### 5.10 시즌 2 — Shell · Vim (2026-10-28 사용자 승인)

Git 시즌 1은 25세트로 신규 확장을 멈춘다. 마감 수정은 #65(인용·이스케이프·옵션 값)와 #66(미션 재시작)이며, #64·#67·#68은 유지보수 후순위로 둔다. 공개 준비(도메인·분석 등)는 시즌 확장과 별도로 관리한다.

- **Shell 기준:** Bash + GNU 도구. macOS 기본 도구와 다른 옵션은 해설에서 밝힌다. SSH는 연결 없이 해설에서 안내한다. 실제 원격 연결과 범용 셸 실행기는 만들지 않는다.
- **학습 흐름:** 기존 따라치기·뜻 보고 치기·SRS·기록을 재사용한다. 각 세트는 `~/workspace` 아래의 새 연습 폴더에서 시작한다. 명령마다 실제 출력과 명령 뒤 파일 트리·현재 경로를 표시한다. 심볼릭 링크와 파일 내용 미리보기는 초기 범위에 없다.
- **콘텐츠 검증:** `content/stories/shell/<슬러그>.sh`는 신뢰하는 저장소 콘텐츠다. `scripts/lib/shell-story.ts`가 매번 별도 임시 디렉터리에서 실제 Bash + GNU find로 실행하고 제거한다. 임시 루트 경로만 `~/workspace`로 치환하고 끝 줄바꿈을 제거한다. `npm run validate:shell` 또는 `npx tsx scripts/shell-story-check.ts <슬러그>`로 명령·종료 상태·출력·현재 경로·파일 트리를 비교한다. build에서도 필수 실행한다. 브라우저 입력은 실행하지 않는다.
- **Shell 판정:** Git 토크나이저를 재사용하지 않는다. `$HOME`과 `'$HOME'`, `>`와 `\>`처럼 뜻이 다른 입력을 섞지 않도록 앞뒤 공백만 무시하고 명시한 정답과 비교한다. 추가 동의어는 검증 후 answers에 넣는다. 파일 상태의 경로는 상대 경로이며 공백이 있는 파일 이름을 허용한다. 중복·부모 누락·트리에 없는 cwd·절대 경로를 검증한다.
- **Vim 구현 방향:** 문자열 따라치기 대신 실제 키 이벤트로 움직이는 미니 편집기. `src/core/vim`은 본문·커서·모드의 순수 상태 전이, UI는 키 수집·표시를 맡는다. Esc·Ctrl 조합은 문자 표기가 아니라 키 동작으로 다룬다. 결과 본문·커서·모드를 채점하고 실제 Vim과 대조한다. 전체 Vim, 플러그인, 실제 파일 접근은 범위 밖이다. 이동·편집·undo·검색 상태를 검증한 뒤 입문 4세트를 만든다.

첫 공개 단위는 **Shell 카테고리 + 기초 2세트(#70)**. Shell 후속 6세트(#71)까지 구현해 총 8세트·따라칠 명령 180개·도전 37문제가 있다. 다음 순서는 Vim 미니 편집기·4세트(#72)다. 파일 트리 상태는 `fileState`, 목록은 `content/curriculum/shell.yaml`에 둔다.

Shell 후속 보강(#71):
- 읽기·grep·find·파이프·인용·종료 상태 6세트를 실제 Bash로 기록한다. `less -F -X`는 짧은 파일의 출력만 연습하며 less 키 조작이나 계속 기다리는 `tail -f`는 실행하지 않는다. 검증 환경에는 Bash·GNU 도구(find/grep/sed/coreutils)·less가 필요하다.
- copy 항목의 `exitCode`는 기대 종료 상태(0~255, 기본 0)다. `grep -q`의 일치 없음 1·파일 읽기 실패 2, cat의 읽기 실패 1을 구분해 설명하고 명령 아래에 상태를 표시한다. 명시하지 않은 실패는 검증 오류다.
- 세트 완료 시 마지막 명령의 종료 상태·파일 트리를 확정한 뒤 결과 화면으로 전환한다. 자식의 줄 변경 effect에만 의존해 마지막 상태가 남지 않던 문제를 파이프 세트 E2E로 재현해 수정했다.
- 기록용 명령이 `$?`를 덮어쓰던 문제를 실제 Bash 대조 테스트로 재현해 고쳤다. 다음 학습 명령 직전에 직전 상태를 복원한다. `PIPESTATUS`는 계측이 덮어쓰기 전에 **같은 학습 명령 안에서** 바로 읽는 예시만 사용한다. `set -e`와 별도 프로세스·대화형 프로그램의 일반 실행을 흉내 내는 도구는 아니다.
- `find`의 순서는 보장하지 않으므로 목록 출력에는 `sort`를 명시한다. 새 6세트는 별도 공통 초기 자료(service-fixtures.sh)를 사용해 기존 기초 2세트의 출력을 바꾸지 않는다. 공백 경로·빈 파일·권한 600인 설정 파일도 준비한다.

## 7. 작업 방식

- 마일스톤 하나 = 이슈 1개 + 브랜치 1개(`m1-typing` 식) → PR(미리보기 확인) → main 병합·배포

- 작업 트리는 M3를 M1·M2와 병행할 때처럼 실제로 동시에 진행할 때만 만든다. 만들기 전에 `git worktree list`로 쌓인 게 없는지 본다
- core는 테스트를 먼저 쓰고 구현한다
- 마일스톤이 끝나면 계획서의 체크박스와 이 문서를 함께 갱신한다
