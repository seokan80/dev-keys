## 0. 확정된 결정 사항

| 항목 | 결정 |
|---|---|
| 정체성 | **개발자 전용** 타자 연습. 일반 한글/영문·일반 회화 타자는 하지 않음 |
| 모드 | **기본 모드** = 따라치기 / **도전 모드** = 뜻 보고 치기 + 미션 |
| 답 입력 | 객관식 없음. 답은 항상 타이핑 |
| 세션 | 1세트 약 3분 → 결과 화면 → 다음 세트 추천 |
| 손가락 안내 | 손 이미지 오버레이 **하지 않음**. 손가락별 색 키보드 + 다음 키 강조 + 손가락 이름 표시 |
| Git | 명령 입력 시 커밋 트리가 바뀌는 시각화. 미션 채점은 **결과 트리 비교** |
| 순위 | MVP 제외. 2차에 **일간 챌린지 + 닉네임 순위** |
| 운영 비용 | MVP는 정적 사이트로 **0원** 목표 |

## 1. 범위

### MVP (1차 공개)
- 기본 모드: Git 따라치기, 코드 따라치기 1종(Java·Spring 또는 React 중 택1)
- 도전 모드: Git 뜻 보고 치기, Git 트리 미션 5~10개
- 손가락 가이드 키보드
- 결과 화면, 개인 최고 기록, 오답 반복 출제 (브라우저 저장)
- 세트별 고유 URL + 해설 페이지
- 배포, 분석, SEO 기본

### 2차
- 일간 챌린지 + 닉네임 순위 (백엔드 도입)
- 애드센스 적용
- 코드 따라치기 2종째 추가

### 이후
- Vim(미니 편집기), Linux 셸, SQL, 정규식, 개발자 영어
- 주간·분야별 순위

### 하지 않는 것
- 회원가입/로그인 (2차도 닉네임만)
- 충돌 해결 시뮬레이션, 실제 원격 저장소 연동
- 모바일 타이핑 지원 (모바일은 해설 열람만, 연습은 PC 안내)

## 2. 기술 스택 (제안)

> 개발 착수 전 M0에서 최종 확정. 아래는 권장안과 근거.

| 영역 | 권장 | 근거 / 대안 |
|---|---|---|
| 프레임워크 | **Astro + React(아일랜드) + TypeScript** | 세트별 페이지를 정적 생성(SEO), 해설은 마크다운, 타이핑 화면만 React로 동작. 대안: Vite+React SPA + 프리렌더 |
| 스타일 | Tailwind CSS | 손가락 색 토큰 관리 쉬움 |
| 상태 | React 내부 상태 + 작은 스토어(Zustand 등) | 전역 상태 적음 |
| 콘텐츠 | YAML/MDX + **zod 스키마 검증** | 빌드 시 문제 데이터 오류 차단 |
| Git 엔진 | **순수 TS 자체 구현** | 범위 한정(명령 8개), 단위 테스트 필수 |
| 트리 렌더링 | **SVG 직접 렌더 + CSS 트랜지션** | 레이아웃이 단순(세로 커밋 레인). 필요 시 애니메이션 라이브러리 |
| 저장 | localStorage (버전 붙인 스키마) | 로그인 없음 |
| 테스트 | Vitest(단위), Playwright(E2E) | 엔진·채점은 단위 테스트, 핵심 흐름은 E2E |
| 호스팅 | **Cloudflare** 정적 호스팅 | 무료, CDN, 미리보기 배포. 대안: GitHub Pages, Vercel |
| 2차 백엔드 | **Cloudflare Workers + D1** | 호스팅과 같은 플랫폼으로 통일. 대안: Supabase(무료 프로젝트는 비활성 시 일시정지 정책 확인 필요) |
| 분석 | Cloudflare Web Analytics | 무료, 쿠키 없음 |
| 오류 수집 | (선택) Sentry 무료 티어 | 공개 후 필요 시 |

## 4. 핵심 모듈 설계

### 4.1 타이핑 엔진
- 입력 단위: 문자. 목표 문자열과 한 글자씩 비교
- 상태: `대기 → 진행 → 줄 완료 → 세트 완료`
- 오타 처리: 틀린 글자는 빨간색 표시, **백스페이스로 수정해야 진행** (정확도 습관)
- 지표
  - **타수(분당)** = 정확히 입력된 문자 수 ÷ 경과 분
  - **정확도** = 정확 입력 ÷ 전체 입력(백스페이스 제외)
- 공백·탭: 코드 들여쓰기는 자동 입력(사용자는 줄 내용만 침) — 옵션으로 켜고 끌 수 있게
- IME: 한글 입력 상태 감지 시 "영문 입력으로 전환" 안내

### 4.2 손가락 가이드 키보드
- 데이터: 키 배열(기본 영역만, 86키·풀배열 공통) + `키 → 손가락` 매핑 테이블
- 손가락 10색 토큰 (왼손 새끼~엄지, 오른손 엄지~새끼)
- 표시 규칙
  - 전체 키를 담당 손가락 색으로 연하게 칠함
  - 다음에 칠 키는 진하게 + 테두리 강조
  - Shift 필요 문자는 **반대 손 Shift + 해당 키** 동시 강조
  - 키보드 아래에 "오른손 약지 + 왼손 새끼(Shift)" 텍스트 표시
- 숫자줄 6: 오른손 검지로 기본 설정, 설정에서 왼손 검지로 변경 가능
- 설정에서 키보드 숨김 가능 (숙련자용)

### 4.3 Git 엔진
- 지원 명령 (MVP)
  `commit`, `branch <name>`, `branch -d`, `switch <name>`, `switch -c <name>`, `checkout <name>`, `checkout -b <name>`, `merge <name>`, `rebase <name>`, `cherry-pick <ref>`, `reset [--soft|--hard] <ref>`, `revert <ref>`
- ref 표기: 브랜치명, `HEAD`, `HEAD~n`, `HEAD^`, 커밋 라벨(C1, C2…)
- 상태 모델
  ```ts
  type Commit = { id: string; parents: string[]; label: string }
  type RepoState = {
    commits: Record<string, Commit>
    branches: Record<string, string>   // 브랜치명 → 커밋 id
    head: { type: 'branch'; name: string } | { type: 'detached'; commit: string }
  }
  ```
- API: `execute(state, input) → { state, events, error? }`
  - `events`: 렌더러용 애니메이션 이벤트 (커밋 생성, 포인터 이동, 커밋 복사, 고아 커밋 발생)
  - `error`: 잘못된 명령이면 실제 git과 비슷한 메시지
- 위험 명령 연출: `reset --hard`로 고아가 된 커밋은 회색 처리 후 사라지는 이벤트 발행
- 제외: 충돌, 스테이징 영역, 원격(`push`/`pull`은 "이 모드에서는 지원하지 않음" 안내)

### 4.4 트리 미션 채점
- **결과 트리 비교**로 판정 (어떤 명령을 썼든 같은 결과면 정답)
- 비교 기준
  1. 브랜치 이름 집합과 각 브랜치가 가리키는 커밋의 **구조적 위치**
  2. HEAD 위치
  3. 커밋 그래프 형태(부모 관계). 새로 만든 커밋은 id 대신 **"원본 커밋에서 복사됨" 관계**로 매칭 (rebase/cherry-pick 결과 비교용)
- 점수 = 성공 여부 × (기본 점수 + 남은 시간 보너스 − 명령 수 초과 감점)
- 미션 데이터는 "시작 상태 + 목표 상태 + 제한 시간 + 권장 명령 수 + 해설"

### 4.5 도전 모드: 뜻 보고 치기
- 문제: 설명 → 정답 명령(복수 허용)
- 판정: 공백 정규화 후 정답 목록과 비교. Git 문제는 **정답 후보들을 엔진으로 실행한 결과 상태 비교**로 동의어 처리(`switch -c` = `checkout -b`)
- 힌트: 첫 글자 공개(감점), 정답 보기(0점 + 오답 등록)

### 4.6 점수
- 기본 모드: 점수 없음, 타수·정확도·최고 기록만
- 도전 모드 세트 점수 = Σ(문제 점수) × 정확도 보정
- 공식은 `core/scoring`에 모아 두고 2차 순위에서 서버도 같은 공식을 사용

### 4.7 오답 반복 (간이 SRS)
- 문제별 `{ 틀린 횟수, 마지막 정답일, 간격 }` 저장
- 세트 구성 시 간격이 지난 오답을 30%까지 섞어서 출제
- 저장은 `storage` 모듈 경유, 스키마 버전 필드로 마이그레이션

## 5. 콘텐츠 데이터 형식

### 세트 (`content/sets/git/basic-branch.yaml`)
```yaml
id: git-basic-branch
category: git
title: 브랜치 만들고 이동하기
level: 1
guide: git/basic-branch        # 해설 MDX 경로
items:
  - type: copy                  # 기본 모드
    text: git switch -c hotfix
  - type: recall                # 도전 모드
    prompt: 새 브랜치를 만들고 바로 이동
    answers: ["git switch -c <name>", "git checkout -b <name>"]
    placeholder: { name: hotfix }
```

### 미션 (`content/missions/git/hotfix.yaml`)
```yaml
id: git-mission-hotfix
title: 운영 긴급 수정 반영
timeLimitSec: 60
recommendedCommands: 4
start: { ... RepoState ... }
goal:  { ... RepoState ... }
guide: git/mission-hotfix
```

- 빌드 시 zod로 전부 검증, 미션은 **"권장 풀이를 엔진으로 실행하면 goal과 일치하는지"** 테스트로 자동 확인
- 콘텐츠 작성은 AI로 초안 생성 → 직접 검수

### MVP 콘텐츠 분량
- Git 명령 세트 6~8개 (명령 약 50개)
- Git 미션 5~10개
- 코드 세트 4~6개 (1종)
- 해설 페이지: 세트 수와 동일 (10~20개)

## 8. 배포 전략

### 환경
| 환경 | 트리거 | 용도 |
|---|---|---|
| Preview | PR 생성/갱신 | 기능 확인, 공유용 임시 URL |
| Production | main 병합 | 실서비스 |

### 파이프라인 (GitHub Actions)
```
PR  → lint → typecheck → unit test → content 검증(zod + 미션 풀이) → build → preview 배포 → E2E(preview 대상)
main → 위와 동일 → production 배포
```
- 콘텐츠 검증 실패 시 배포 차단 (잘못된 문제가 나가는 것이 가장 큰 사고)
- 롤백: Cloudflare 대시보드에서 이전 배포로 즉시 되돌리기, 또는 revert 커밋

### 도메인
- 1안: 기존 블로그 도메인의 서브도메인 (예: `typing.seokan.dev`) → 비용 0원
- 2안: 별도 도메인 (브랜딩이 필요해지면) → 연 2만 원 안팎
- DNS를 Cloudflare에서 관리하면 연결이 가장 간단

### 공개 체크리스트
- [ ] 모든 세트·미션 페이지 정상 렌더 (E2E 크롤)
- [ ] Lighthouse 성능·접근성 90 이상
- [ ] sitemap 제출 (Google Search Console, 네이버 서치어드바이저)
- [ ] 개인정보처리방침 게시 (광고·분석 사용 내용 포함)
- [ ] 키보드 레이아웃 확인 (Windows/Mac, 86키/풀배열)
- [ ] 한글 입력 상태 안내 동작

## 9. 운영 전략

### 지표 (Cloudflare Web Analytics + 자체 이벤트)
| 지표 | 목표 | 의미 |
|---|---|---|
| 일 방문 | 30명 이상 | 비용 회수 기준선 |
| 방문당 세트 수 | 2 이상 | 다음 세트 추천이 작동하는지 |
| 검색 유입 비중 | 증가 추세 | 세트별 URL·해설 전략 검증 |
| 세트 완료율 | 60% 이상 | 3분 길이·난이도가 적절한지 |
| 카테고리별 방문 | — | 다음에 추가할 모드 결정 근거 |

### 콘텐츠 운영
- **주 1회 세트 또는 미션 1~2개 추가** (AI 초안 → 검수 → PR)
- 유입 많은 카테고리 우선 확장
- 오탈자·정답 오류 신고: 결과 화면에 "문제 신고" 링크 (GitHub 이슈 또는 폼)

### 비용 관리
| 항목 | MVP | 2차 |
|---|---|---|
| 호스팅 | 0원 | 0원 (무료 한도 내) |
| DB/API | 없음 | Workers·D1 무료 한도 내 예상 |
| 도메인 | 0원(서브도메인) | — |
- 무료 한도의 70% 도달 시 알림 설정

### 2차 순위 운영
- 공정성: 순위는 **일간 챌린지(모두 같은 문제)** 에만 적용
- 부정 방지(간이)
  - 점수와 함께 키 입력 타임라인 제출 → 서버에서 같은 공식으로 재계산
  - 사람이 낼 수 없는 속도(예: 키 간격 비정상적으로 일정·과도하게 빠름)는 제외
  - 닉네임 비속어 필터, 신고 시 수동 삭제
- 완벽한 방지는 목표로 하지 않음 (취미 서비스 수준)

### 광고 운영 (2차)
- 위치: 결과 화면, 해설 영역만. 타이핑 중 화면 절대 금지
- 해외(유럽 등) 방문자 대상 동의 배너 요구사항은 신청 시점에 확인
- 수익은 기대하지 않고 비용 회수 확인용으로만 관찰

### 정기 점검 (월 1회)
- 의존성 업데이트, 빌드 확인
- 지표 리뷰 → 다음 달 콘텐츠·모드 우선순위 결정
- 무료 한도 사용량 확인

## 10. Claude Code 작업 가이드

### `CLAUDE.md` 초안
```markdown
# DevKeys

개발자용 타자 연습 웹. 기획·결정 사항은 docs/개발계획서.md 기준.

## 규칙
- 로직은 src/core에, UI는 src/components에. core는 React·브라우저 API 의존 금지
- core 변경 시 단위 테스트 필수. Git 엔진은 명령별 테스트 + 결과 비교 테스트
- 콘텐츠(YAML/MDX) 추가 시 zod 스키마 검증 통과 필수, 미션은 권장 풀이 테스트 추가
- 타이핑 화면 근처에 광고·팝업 요소 배치 금지
- 범위 밖 기능(로그인, 충돌 시뮬레이션, 원격 저장소)은 구현하지 않음
- UI 문구는 한국어

## 명령
- dev: npm run dev
- test: npm run test / npm run test:e2e
- 콘텐츠 검증: npm run validate:content
```

### 진행 방식
1. 마일스톤 하나씩 진행, 각 마일스톤을 **이슈 1개 + 브랜치 1개**로
2. 시작 시 "M1 진행, 7장 체크리스트 기준"처럼 범위를 명확히 지시
3. core 로직은 **테스트 먼저 작성 → 구현** 순서 요청
4. 마일스톤 종료 시 이 문서의 체크박스 갱신

### 착수 첫 지시 예시
> docs/개발계획서.md 를 읽고 M0을 진행해줘. 2장 기술 스택은 권장안 그대로 사용하고, 끝나면 완료 기준 충족 여부를 보고해줘.
